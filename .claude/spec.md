Pythonベースのライブコーディング・オーケストレーター（コードDJシステム）構築のための仕様書。本システムは、ロジックをリアルタイムに音楽と映像へ変換し、即興的な演奏を可能にすることを目的とします。

---

## 1. プロジェクト概要

**プロジェクト名：** PyCodeDJ (仮)

**目的：** Pythonコードの構造的特徴をリアルタイムに可聴化（Sonification）および可視化（Visualization）し、`# @loop` ブロックの即時評価を演奏操作として扱えるDJスタイルのパフォーマンス環境を実現する。

**差別化ポイント：**
既存のPython↔SuperCollider橋（sc3nb・supriya）はコードから音響エンジンを操作するAPIを提供するが、PyCodeDJの独自価値は以下の3点に集中させる。

1. **ブロック評価演奏** — `# @loop` マーカーで区切ったブロック単位でコードを即時評価・送出する。演奏者が意図したときだけ音が変わる。ファイル保存に依存しない。
2. **コード構造の可聴化** — コードの構造的特徴（複雑度・深さ・パターン）を音楽パラメーターに変換する。「何を書くか」が「どう聴こえるか」に直結する。
3. **複数ループの独立制御** — ブロックごとに独立した `LiveLoop` が走る。あるブロックを更新しながら、他のブロックはそのまま鳴り続ける。

**MVPの焦点：**
初期バージョンでは、すべてのコード特徴量を音楽化することを目指さない。まずは「ブロックを即時評価した結果が、止まらないループの音色・密度・揺らぎとして知覚できる」ことを成立条件とする。テンポや基音のような楽曲全体を壊しやすい要素は、初期段階では演奏者が明示的に制御する。

---

## 2. システムアーキテクチャ

システムは「制御層」「音響層」「視覚層」の3層構造とし、各層間はOSC（Open Sound Control）プロトコルにより疎結合で連携します。

| 層 | 役割 | 主要コンポーネント |
| :--- | :--- | :--- |
| **制御層 (Python)** | ユーザーコードの解析、スケジューリング、OSC命令の送出 | Python 3.x, python-osc, ASTモジュール, tokenize |
| **音響層 (Engine)** | リアルタイム音響合成、エフェクト処理 | SuperCollider (scsynth) |
| **視覚層 (Visual)** | 音楽データに同期したグラフィックス生成 | Hydra (JavaScript/GLSL) または Pyxel (Python) |

**タイミング設計の方針：**
BPMクロックはSuperCollider側（`TempoClock`）が保持する。Pythonの役割は「`pycodedj eval` が呼ばれたタイミングで、次回ループから使う音楽パラメーターをOSCで送ること」のみとする。Pythonは周期イベントを自ら刻まない。GIL・GCポーズによるジッターを避けるため、定期的なビートの刻みはすべてSuperColliderに委ねる。

## 3. 主要機能要件

### ① ブロック評価・ライブ実行機能

**ブロック形式：**

```python
# @loop bass interval=2.0
def bass():
    for i in range(8):
        if i % 2 == 0:
            pass

# @loop melody interval=0.5
def melody():
    x = 1
    y = 2
    return x + y
```

- `# @loop <名前> [interval=秒]` から次の `# @loop` までを1ブロックとして扱う。
- ブロック評価のトリガーはMVPでは以下の1方式のみとする。
  - **CLIコマンド（MVP）:** `pycodedj eval <file>::<loop名>` で指定ブロックを即時評価・送出する。
- 評価の内容はAST解析と特徴量抽出のみとする。コードを `exec` しない。
- 評価時は、構文エラー・AST解析エラーによって他のループが停止しないよう、直前の有効パラメーターへフォールバックする。
- ブロックを評価するとそのループが再起動し、他のループはそのまま継続する。

> **将来対応（MVP外）：** エディタキーバインド（VS Code 拡張）によるカーソル位置のブロック評価。ファイル保存トリガーによる自動評価。

### ② スケジューリングエンジン

- BPMクロックはSuperCollider側が保持し、Pythonはパラメーター更新のトリガーに徹する。
- Pythonは `pycodedj eval` 実行時に一度だけOSCを送る。周期送信はしない。
- `LiveLoop` はループ名と interval を保持するが、周期的にOSCを送るのはSuperCollider側のルーティンが担う。Python側の `LiveLoop` は「最後に送ったパラメーターの状態管理」と「ループの停止・再起動管理」に限定する。

### ③ コード解析・マッピング機能（音楽的マッピング設計）

コードの構造的特徴を音楽パラメーターに変換する。マッピングは「音楽的に意味のある対応」と「演奏者が予測・制御できること」を基本方針とし、機械的な数値の割り当てにとどまらない設計とする。

**マッピング仮説（フェーズ0で検証する）：**

| コード特徴量 | 抽出方法 | 対応音楽パラメーター | 音楽的根拠 |
| :--- | :--- | :--- | :--- |
| ネストの深さ（最大） | ASTノード深さ | フィルターCutoff | 深い構造＝複雑さ＝音色の明るさ・開放感 |
| 制御フロー数（if/for/while） | ASTノード数 | LFOレート | 分岐の多さ＝揺らぎの速さ |
| 関数定義数 | ASTノード数 | ポリフォニー声部数 | 関数＝独立した声部 |
| コメント率 | tokenize（COMMENT トークン数 / 実効行数） | リバーブDepth | 余白の多さ＝空間の広さ |

**初期採用を保留するマッピング：**

| コード特徴量 | 保留する対応 | 保留理由 |
| :--- | :--- | :--- |
| 行数（実効行） | テンポ（BPM） | テンポは楽曲全体の土台であり、評価のたびの意図しない変化が演奏を壊しやすい |
| 変数名の長さ（平均） | Pitch（基音） | 命名スタイルと音高の関係が弱く、演奏者が音楽的に制御しにくい |

> これらの仮説はフェーズ0での試演・聴取によって検証・修正する。音楽的に不自然に聴こえるマッピングや、演奏者が予測しづらいマッピングは廃止し、演奏として機能するものだけを残す。

### ④ 外部連携（OSCブリッジ）

**OSCアドレス設計：**
複数ループが同じアドレスを上書きしないよう、ループ名をアドレスに含める。

```
/pycodedj/loop/<name>/cutoff      float  Hz, 200–4000
/pycodedj/loop/<name>/lfo_rate    float  Hz, 0.1–5.0
/pycodedj/loop/<name>/reverb      float  0.0–0.8
/pycodedj/loop/<name>/voice_count int    1–4
```

SC側は loop 名ごとに独立したシンセを持ち、該当アドレスへのOSCを受信したときそのシンセのパラメーターだけを更新する。

- ビジュアライザー（Hydra）へは同じパラメーターを別ポートに送出する。
- 目標はサンプル精度の完全同期ではなく、ライブ演奏上「知覚上同期している」と感じられる精度とする。

## 4. 技術スタック

- **開発言語:** Python 3.10+
- **音響バックエンド:** SuperCollider (scsynth)
- **通信プロトコル:** UDP (OSC)
- **推奨OS:** Linux (Raspberry Pi 5等) または macOS (Core Audioの低遅延性を活用)
- **ライブラリ（必須）:**
  - `python-osc`: OSC通信用
  - `threading`: LiveLoop の状態管理用
- **ライブラリ（オプション）:**
  - `watchdog`: ファイル保存トリガーを使う場合（MVP外）

## 5. ロードマップ

### フェーズ0：マッピング設計の検証（着手前必須）

フェーズ1に入る前に、ASTマッピング仮説が「音楽として聴こえる」かを確認する。

- SuperColliderで数種のシンセを用意し、手動でパラメーターを変化させて聴取する。
- セクション3の仮説マッピングに沿ってパラメーターを変えたとき、音楽的な変化として感じられるかを確認する。
- 機能しないマッピングは廃止し、代替案を決定してから次フェーズへ進む。
- 3つ程度のコード断片を用意し、`pycodedj eval` を実行するたびに音色・密度・揺らぎの違いが明確に知覚できる最小デモを作る。
- フェーズ0の合格条件は、演奏者が「どのコード変更がどの音楽変化を起こすか」をおおまかに予測できることとする。

### フェーズ1：プロトタイプ開発（最短1週間）

- SuperColliderの起動と、Pythonからの単発音（サイン波等）の鳴動確認。
- OSC経由でのパラメーター変更の実装。loop 名を含むアドレス形式（`/pycodedj/loop/<name>/cutoff`）で動作することを確認する。
- SuperCollider側でTempoClock（BPMクロック）を管理する構成を確認する。

### フェーズ2：ブロック評価エンジンの実装

- `# @loop` ブロックパーサーの実装。
- `pycodedj eval <file>::<loop名>` CLIコマンドの実装。
- AST解析 → マッピング → OSC送出のパイプライン実装。
- 複数ループの独立起動・停止の実装。

### フェーズ3：ビジュアライザー統合

- Hydra等の外部ツールへのOSC送信。
- 音と映像がライブ演奏上自然に同期して見える環境の構築。

### 将来対応（MVP外）

- VS Code 拡張：カーソル位置のブロックを Cmd+Enter で評価する。
- ファイル保存トリガー：保存検知による自動評価（`watchdog` 使用）。

---

> **例え話：指揮者とオーケストラ**
> このシステムにおいて、**Pythonコードは「指揮譜（楽譜）」**、**Pythonエンジンは「指揮者」**、**SuperColliderは「オーケストラ（楽器奏者）」**です。指揮者が楽譜をその場で書き換え、その変更を「今から次の演奏に使え」とオーケストラに伝えます。テンポを刻む責任はオーケストラ側（SuperCollider）にあり、指揮者（Python）は「次に何をするか」の指示を渡すことに集中します。
